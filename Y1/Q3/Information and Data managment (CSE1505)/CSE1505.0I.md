# stuff to know
- indexes
   - sparse, one index per block
   - dense, one index per record
   - primary index, sort stuff by primary index, allows binary search ETC
   - secondary index, must be dense, 
   - for point access (x=5) use hash indexes, hash the index, it gives you the block it's in
   - for point or range, use B+ trees
      - leaf nodes store data, internal nodes only navigation
      - compare key with data, all leafs point to next leaf, this means for range, find begining and end, then just extract all
      - they work like 2-4 trees
   - for multi attribute querys use K-D trees
      - binary tree but every level alternates on which atribute it splits

- query proccessing
   - heuristic optimization
      - basically just apply a bunch of random garbage that may or may not work but superstision say it helps.
      - rules like cartesian project should be a join or subquerys should be a join or select tuples as early as possible 
   - cost-based
      - find out every way we can do the query, then estimate for every query how long it will take, as well as taking intermediate result set size into account
      - cost of index scan is $#mt * (cost_{ix} + 1) + cost_{result}$ OR it's the the amount of blocks
         - where #mt is the expected output of the select
         - cost_{ix} is the height of the tree for K/D & B+ and 0 for hash
      - $cost_{result} = {|R\bowtie S | \over blockingfactor_{result}}$ (this is the cost of storing the intermediate result
         - where the blocking factor is the amount of tuples that fit in a block
      - cost of block nested loop join is $blocks(R) + blocks(R) * blocks(S) + costs_{result}(R\bowtie S)$ (done when no indexes, loop over one table, and nested loop over other table)
      - cost of index nested loop join is $blocks(R) + (|R| * (cost_{ix} + 1)) + costs_{result}(R\bowtie S)$ (loop over one table, use index for inner loop over other table)
      - sorted merge join cost is $blocks(R) + blocks(S) + cost_results(R\bowtie S)$ (only works if both tables are primary index-sorted by the joining attribute, therefore only useable on natural and equi)
      - hash join cost same as sorted merge join, hash the joining column for both tables, if they match the output will be the same, so sort into buckets, then compare everything per bucket, only use on equi and natural 
      - join reduction factors are based on carteasion product vs actual result size

# stuff to memorize
- relational algebra
   - $\sigma$ = select (where atribute, works on rows)
   - $\pi$ = projection (select atribute, works on columns) (projection can't handle duplicates)
   - U = union, merge 2 intermediate result sets
   - $\cap$ = intersection, only output that which is in both inputs
   - \ = set difference, output the union minus intersection
   - $\rho$ = rename, rename a column
      - table can be renamed from R to S using $\rho_s (R)$
      - rename attributes from a,b to A,B by $\rho_{(A,B)} (\pi_{a,b}(R))#
      - both is also an option
   - x = cartesian product
   - $\bowtie$ = join 
      - theta join ($\bowtie$_{<condition>}$) joins both tables where the condition is met
      - natural join ($\bowtie$) is equi join but removes the duplicate attribute in the output
         - if tables both have an attribute with the same name the join will join on that
      - equi join ($\bowtie_{condition}$) like theta but only equals as condition
