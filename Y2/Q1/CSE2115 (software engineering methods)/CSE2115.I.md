- SMART
   - specific: make the goal concrete
   - measurable: objective measure of success
   - achievable: requirement must be achievable with the resources available
   - relevant: contributes to the objective
   - time-bound (might be optional): the expected time-line
- functional requirements are about a service the system provides
- non-functional requirement are about how the system operates; usually things the system shouldn't do or be constrained by
- prioritisation
   - MoSCoW
   - Kano (based on customer satisfaction weighed against implementation cost)
   - rice: reach * impact * confidence / effort
   - WJSF: weighted shortest job first
- architecture:
   - the cost of change is usually what is relavent
   - monolith: theres 1 input, 1 output, everything else happends under the hood
   - distributed: the system consists of different (micro)services which have their own source code, run in their own ecosystem and can have their own release timelines, or even different languages
   - CAP theorem: you cannot have a distributed system be both, available, consistant, AND also have it partition tolerant (partial failure)
- you can partition by technical things. basically organise by capability (business rules, vs persistence, vs presentation)
- or you can partition by domain. basically organise by different parts of the system

- code smells:
   - bloaters: methods and classes that are too large and/or not easy to work with
      - long methods
      - large classes
      - primitive obsession (meeeee :)
      - long parameter list
      - data clumps (parameters that are offten passed together)
   - object-oriented abusers: incomplete or incorrect applications of object-oriented principles
      - complex switch / if cases: any switch case violates open-closed, replace with a class per case, have them override the method (or consider pulling from file)
      - temporary fields
      - refused bequest
   - change-preventors: changes to some parts require many changes in other parts too
      - divergent change
      - parallel inheritance hierarchies
      - shotgun surgery
   - dispensable: classes and methods that are not necessary (not bloat)
      - commented out code
      - duplicate code
      - lazy class
      - data class
      - dead code
      - speculative generality
   - couplers: classed and methods with very high coupling
      - feature envy: method that cares more about other classes than itself
      - inappropriate intimacy: like bi-directional feature envy: when class A and class B use each other internal fields
      - message chains
      - middleman
- refactoring:
   - extract class: split method into multiple methods
   - extract method
   - introduce parameter object
   - move method: done to reduce coupling, source method becomes delegating
   - replace delegate with inheritance: happends when you should've inherited but instead put a reference to the parent class, inherite, duh (but also not duh because why would a person inherit from phoneNumberHaver
   - replace conditional with ploymorphism
